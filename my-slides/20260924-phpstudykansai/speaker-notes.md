## 3. Pestとは（〜1:15）

「PHPのテストフレームワークです。上が Pest、下が PHPUnit です。Pest は `it()` と `expect()` の Functional Syntax です。見比べるだけにしてください。書き換えが目的ではありません。サイトは pestphp.com です。」

## 4. Pestの特徴（〜1:30）

「特徴は3つ。自然言語に近い構文。PHPUnitからの段階的移行。本体とプラグインに入っている多様な機能。今日話すのは2と3です。」

## 5. PHPUnitからの段階的移行（〜2:00）

「`extends TestCase` のままで、`./vendor/bin/pest` が動きます。公式の Migrating from PHPUnit には、Pest is built on top of PHPUnit、とあります。Drift は PHPUnit から Pest 記法へ変換する公式プラグインです。Rector は移行そのものではなく、リファクタリング用の公式プラグインです。記法の整理と、メジャー間のアップグレードに使います。どちらも、このあとの手順のあとでよい、という位置づけです。」

## 6. 多様な機能がPest本体や公式プラグインに内包（〜2:20）

「記法だけの薄いラッパではありません。速度は `--parallel`、`--shard`、`--profile`、`--compact`。この4つをこのあと見ます。品質には Mutation Testing と Architecture Testing があります。拡張には Laravel、PHPStan、E2E Test があります。今日は速度の4旗に絞ります。」

## 7. セクション：2. Pest導入からCIでの最適化機能活用まで（〜2:30）

「ここから本編です。導入してから、CIの最適化機能を足すところまで。特徴リストの2、3と、この章の番号は別です。手順の1、2、3として聞き直してください。」

## 8. 手順（〜2:45）

「手順は3段です。1、エンジンとして導入する。2、CIを `./vendor/bin/pest --ci` に差し替える。3、最適化機能を足す。」

## 9. 1. Pestの導入（要件）（〜3:00）

「コマンドは短いです。記法の書き換えは後回しでよい。最新の Pest 5 は PHP 8.4 以上が必要です。手順は公式の Installation に沿います。」

## 10. 1. Pestの導入（コマンド）（〜3:25）

「`phpunit/phpunit` を外して、`pestphp/pest` を `--dev` で入れます。`./vendor/bin/pest --init` のあと、`./vendor/bin/pest` で実行します。既存のテストケースはそのまま動きます。」

（画面のコマンドに Laravel プラグインは入っていません。発表者コメントにその文言が残っていても、今日は読み上げません。）

## 11. 2. CIのコマンドの置き換え（〜3:50）

「公式の Continuous Integration にある GitHub Actions の例は、最後が `./vendor/bin/pest --ci` です。PHPUnit からの差分は、この `run` の1行です。`--ci` は、`->only()` によるフォーカスを無視してスイート全体を走らせる旗です。`--tia` は付けません。」

## 12. 3. Pest テスト最適化機能の活用（〜4:10）

「公式の Optimizing Tests に並ぶ4手法です。並列化するのが Parallel Testing と Test Sharding。ボトルネックを把握するのが Profiling。失敗に集中するのが Compact Printer。今日はこの4つです。」

## 13. Parallel Testing（〜4:40）

「いちばん足しやすいのが `--parallel` です。同じ実行環境の中で、テストを複数プロセスで同時に走らせます。画面では、短縮できる可能性がある、までにしておきます。公式の Optimizing Tests は、significantly decrease、greatly reduce、と書いています。効くかどうかはスイート次第です。プロセス数は CPU コア数に合わせて自動でも、`--processes` で指定もできます。」

## 14. Test Sharding（〜5:05）

「次は CI ジョブを増やすやり方です。スイートを分けて、ジョブを並列にします。コマンドは `--shard=1/4`。何分割中の何番目か、だけです。こちらも、短縮できる可能性がある、までにしておきます。」

## 15. Time-Balanced Sharding（〜5:35）

「デフォルトの `--shard` は、件数で割れます。公式の同じ説明では、各シャードがほぼ同じテストファイル数、です。遅いテストが偏ると、一番遅いジョブが全体の時間を決めます。`--update-shards` で時間を記録して、`tests/.pest/shards.json` をコミットします。記録のあと、`--shard` は時間ベースになります。`--update-shards` は記録用なので、毎回の CI には付けません。」

## 16. Profiling（〜6:00）

「`--profile` は高速化そのものではなく、ボトルネック調査です。遅いテストの Top 10 が出ます。画面の 6.27 秒、4.91 秒、全体 11.68 秒は、公式 Optimizing Tests の出力例です。自社の数字ではありません。読み方は、遅い2件でスイートの大半を占めている、です。」

## 17. Compact Printer（〜6:20）

「4つ目が `--compact` です。失敗したテストだけを出して、問題の特定を楽にします。出力が単純になるので、I/O が減り、数ミリ秒速くなることもあります。公式の a few milliseconds です。CI を大きく速くする本命ではありません。」

## 18. 組み合わせるとこうなる（〜6:50）

「組み合わせは、`--parallel` と `--shard` の併用です。`./vendor/bin/pest --ci --parallel --compact --shard=1/4`。4 ジョブに分けて、それぞれ `1/4` から `4/4` を割り当てます。1 ジョブだけで `1/4` だと、スイートの 4 分の 1 しか走りません。`--parallel` と `--shard` の併用は、公式の Sharding 例にあります。`--ci` と `--compact` は、その行に足しています。`--update-shards` は記録用、`--profile` は診断用、`--tia` は用途が違うので、この行には足しません。」

## 19. 補足 TIAモード（〜7:25）

「補足です。TIA は、変更で壊れ得るテストだけを再実行します。Pest 5 の目玉です。今日はスコープ外にします。理由は2つです。1つ、公式は CI のテスト実行コマンドに `--tia` を付けない、と書いています。例外は、ベースラインを記録する専用ジョブだけです。2つ、PHPUnit クラスが残っていると TIA はエラーになります。表示は、Tia mode requires Pest tests、Convert it to a Pest test, or run without Tia、です。プロダクトでもそうなりました。`it()` の中で `$this->assertSame()` を使うだけなら、このエラーの対象ではありません。手順と所要時間の数字には入りません。」

## 20. まとめ（〜7:45）

「3つです。1、Pest は容易な検証と、段階的な導入、移行ができます。2、テストを便利にする機能が、本体と公式プラグインに入っています。3、次は、Pest の導入から、始まる。以上です。」
