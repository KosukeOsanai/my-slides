## 2. 目的

本パネルは、PHP2Shell の技術的な仕組みの解説ではなく、**実際に対応にあたった人の「現場目線」で脆弱性対応を振り返る**ことを主眼に置く。

1. **現場のリアルな一次情報を共有する**
   - ニュースやアドバイザリでは分からない「第一報を見た瞬間の判断」「実際の対応の流れ」「迷ったポイント」を、当事者の言葉で聞く
2. **次の重大脆弱性に備えるヒントを持ち帰ってもらう**
   - 「影響範囲の棚卸し」「関係者との調整」「パッチ適用の判断基準」など、次に同じことが起きたときに使える知見を会場に残す
3. **「PHP本体の脆弱性」をアプリ開発者が自分ごと化するきっかけにする**
   - フレームワークやCMSの更新だけでは済まず、ランタイム（PHP本体）の更新が必要だったという点に目を向けてもらう

### 背景: PHP2Shell とは（おさらい用・要再確認）

> オープニングで共通認識をそろえるための最小限の情報。深掘りはしない。

> 以下は2026/10/28時点の公開報道ベースの整理。当日までに PHP 公式アドバイザリ・NVD で数字と日付を再確認する。

- PHP 本体に見つかった 2 件の重大な脆弱性の通称（CVE-2026-109618 / CVE-2026-109619）
  - CVE-2026-109618: out-of-memory 時のメモリ破損によるリモートコード実行
  - CVE-2026-109619: 古いグローバル状態（stale global state）が残ることによるリモートコード実行。セッションのアップロード進捗機能経由で FPM 上でも成立すると報告されている
- 深刻度: ベンダー評価で CVSS v4.0 9.2（評価機関によって差あり）
- 2026/10/21 に修正版 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 がリリース
  - EOL 版（7.4 / 8.0 / 8.1）向けのバックポートやディストリビューション独自パッチの情報もあり
- PHP 5.4 時代から存在していたバグとの報道あり
- 修正版の公開から数日後に、関連する別の脆弱性（CVE-2026-115560）への注意喚起と暫定策（アップロード進捗機能の無効化）が出たとの報道あり
- **ポイント**: WordPress やフレームワーク、プラグインの更新では直らない。PHP 本体の更新が必要

## 5. 各テーマの問いかけ案（ファシリ手持ち）

全部聞く必要はない。事前打ち合わせでパネラーが話しやすいものを2〜3問ずつに絞る。

### テーマ1: 脆弱性を見たとき、どう思ったか（5分）

- 最初にどこで知りましたか？（SNS／社内Slack／ベンダー通知／ニュース）
- 第一印象は？「やばい」と思ったか、「うちは関係ないかも」と思ったか
- 「PHP本体の脆弱性」と聞いて、アプリ側の脆弱性とどう違う緊張感がありましたか？
- 自分たちの環境が影響を受けるかどうか、どのくらいで判断できましたか？

### テーマ2: 現場でどういう対応をしたか（8分）

- 最初の1時間／当日／1週間で何をしましたか？
- 影響範囲の棚卸しはどうしましたか？（PHPのバージョン・SAPI・どこで動いているか把握できていたか）
- 誰と調整が必要でしたか？（インフラチーム、ホスティング事業者、顧客、経営層）
- 修正版を待つ間や、すぐに上げられない環境で、暫定策（WAF、設定変更など）は取りましたか？
- 攻撃の痕跡（ログ）の確認はしましたか？どこまでやりましたか？
- 「やっておいてよかった」こと、「やっておけばよかった」こと

### テーマ3: パッチ適用にあたって何が懸念点だったか（7分）

- パッチ版（マイナーアップデート）を当てること自体に不安はありましたか？
- 検証環境での確認はどこまでやりましたか？ リリース判断の基準は？
- ディストリビューションのパッケージ待ちか、公式版を自前ビルドか、コンテナイメージ更新か
- EOL のPHPバージョンが残っていた場合どうしましたか？（バックポート／移行の前倒し）
- 止められないサービス・メンテナンス時間の確保はどう調整しましたか？
- 修正後に関連する脆弱性の続報が出たことで、追加対応は発生しましたか？

### クロージング（4分）

- 「次に同じレベルの脆弱性が出たら、今回の経験から何を変えますか？」を一言ずつ
- ファシリまとめ: 3つくらいのキーワードに集約して締める（例:「棚卸し」「判断の速さ」「ランタイムも依存関係」）

### 予備の質問（①〜③が話せなかったとき用）

PHP2Shell ならではの特徴（PHP 本体の脆弱性、影響バージョンの広さ、デフォルト有効の設定経由、修正前からの悪用報道、続報の CVE など）に絡めた質問。「何をしたか」は話せなくても「どう判断したか」「どこが難しかったか」なら話せることが多いので、判断の理由を聞く形にしている。事前打ち合わせで「これなら話せる」ものに印を付けてもらう。★は優先して使いたい質問。

> 質問に含まれる数値・日付・技術的な前提は報道ベース。使う前に公式アドバイザリで裏取りし、違っていたら言い回しを直す。

#### A. 「うちは該当するのか」の切り分け

- ★「PHP 5.4〜8.5 が影響」という範囲の広さを見て、該当する／しないを何で切り分けましたか？（バージョン／SAPI／設定／外部公開しているか）
- ★CVE-2026-109619 は、デフォルトで有効なセッションのアップロード進捗機能（`session.upload_progress.enabled`）経由で成立すると言われています。この設定を意識したことはありましたか？ 自分たちの環境で有効かどうか、どう確認しましたか？
- FPM 環境で成立するかは、解析によって見解が割れていました。「影響あり」とみなして動くか、情報がそろうのを待つか、どう決めましたか？
- 「認証なし・リモートから」という条件は、社内向けシステムや管理画面しかないサービスの優先度付けをどう変えましたか？
- CLI のバッチ、社内ツール、昔立てた WordPress のサイトなど、「メインの Web アプリ以外の PHP」はどこまで対象に入れましたか？ 見つけるのに苦労した場所は？

#### B. 深刻度と情報の読み方

- CVSS はベンダー評価で 9.2（v4.0）、NVD では 9.8／8.1（v3.1）、10 と評価する調査会社も、と数字がばらつきました。数字の違いは対応の優先度に影響しましたか？
- ★「修正版の公開前から悪用の試みが観測されていた」との報道がありました。「パッチを当てて終わり」ではなく「すでに侵入されているかも」という前提で動きましたか？
- GitHub に PoC やチェックツールを名乗るリポジトリが大量に出ました。自分たちの環境の確認に使いましたか？ 偽物・マルウェア入りの可能性はどう警戒しましたか？

#### C. 時間との戦い

- ★修正版の公開は日本時間の夜（21日 23:00 ごろ、要確認）だったとの情報があります。その夜のうちに動きましたか、翌朝からにしましたか？ その判断の理由は？
- 前日に事前告知が出ていたとの情報があります。修正版が出るまでの間に準備できたことはありましたか？
- 海外では政府系サイトをオフラインにした例も報じられました。「いったん止める」という選択肢は検討しましたか？ 検討したならどんな条件で？

#### D. 「PHP 本体の脆弱性」ならではの難しさ

- ★ライブラリなら `composer update` で済むところ、今回はランタイムの更新でした。誰の担当になりましたか？（アプリチーム／インフラチーム／ホスティング事業者）押し付け合いや抜け漏れは起きませんでしたか？
- 公式 Docker イメージを使っている場合、イメージの更新を待ちましたか？ ベースイメージを差し替えて全サービスを再ビルド・再デプロイするのは大変でしたか？
- ★パッケージを更新しても、動いているプロセスが古いままでは直りません。php-fpm や常駐型の実行環境（FrankenPHP のワーカーモード、RoadRunner、Swoole など）の再起動まで確認しましたか？
- 「本当に直った」はどう確認しましたか？ ディストリビューションのバックポート版はバージョン番号が変わらないので、`php -v` やスキャナーの結果と食い違うことはありませんでしたか？
- WordPress などの CMS を使っているお客さんやチームに「プラグインやテーマを更新しても直らない」と伝える必要はありましたか？ どう説明しましたか？

#### E. 暫定策と、パッチ後の対応

- ★続報の CVE-2026-115560 には専用パッチがなく、アップロード進捗機能の無効化が暫定策とされていました。この設定をオフにしましたか？ アップロードの進捗表示など、アプリへの影響はどう確認しましたか？
- WAF で防げると判断できましたか？ WAF のシグネチャが出るのを待ちましたか、それとも WAF だけでは不十分と考えましたか？
- メモリ上のパスワードやセッショントークンが漏れる可能性も指摘されていました。シークレットのローテーションやセッションの強制ログアウトまで検討しましたか？
- 「修正前の数日間までさかのぼってログを確認すべき」という記事もありました。どのログの、何を手がかりに見ましたか？（見なかった場合、なぜ見なくてよいと判断したか）

#### F. この脆弱性から見えたこと

- 10 年以上前から残っていたバグだと言われています。「枯れた本体だから大丈夫」という感覚は変わりましたか？
- AI を使った調査で見つかったと報じられています。同じレベルの脆弱性が今後増えるとしたら、今回の対応で何を変えますか？
- EOL のバージョン（7.4／8.0／8.1）向けにもバックポートが出たとのことです。これは「EOL でも何とかなる」という安心材料ですか、それとも早くバージョンアップすべきという警告ですか？

#### 会場を巻き込む質問（パネラーが話しにくいときの場つなぎ）

- 挙手アンケート:「PHP2Shell の対応をした人？」「`session.upload_progress` という設定を今回はじめて知った人？」「修正版を当てたあと、php-fpm の再起動まで確認した人？」
- 手が挙がった人数に対して、パネラーにコメントをもらう（「思ったより多い／少ない」から話を広げる）

#### 話しにくい質問を言い換えるコツ（ファシリ用）

| 話しにくい聞き方 | 言い換え |
|------------------|----------|
| 「御社ではどう対応しましたか？」 | 「一般的には、どう対応するのがよいと思いますか？」 |
| 「攻撃の痕跡はありましたか？」 | 「ログの確認は、どの観点で見るのがおすすめですか？」 |
| 「何台のサーバーを更新しましたか？」 | 「台数が多い環境では、どう進めるのがよいと思いますか？」 |
| 「どこで一番困りましたか？」 | 「もし次に同じことが起きたら、どこが難所になりそうですか？」 |

## 6. 進め方

### 6.1 事前準備スケジュール（案）

開催（11/14）まで約2週間半のため、詰めたスケジュールにしている。所属組織の確認に時間がかかりそうなパネラーには、早めに予備の質問も共有しておく。

| 時期 | やること |
|------|----------|
| 〜10/31 | パネラーへ打診（趣旨・時間・話してほしいテーマ・予備の質問を共有） |
| 〜11/4 | パネラー確定、所属組織への登壇可否・話せる範囲の確認を依頼 |
| 〜11/7 | 事前打ち合わせ（30分程度）: 「7. 事前ヒアリング項目」を使って話す内容と NG 事項をすり合わせ。予備の質問から使うものを選ぶ |
| 〜11/11 | 問いかけを確定してパネラーへ共有。スライド（数枚）作成。事前質問の募集（任意） |
| 11/13〜当日 | 最新情報（追加の CVE・パッチ）を再確認し、おさらいスライドを更新。当日直前に5分だけ最終確認 |

### 6.2 当日の進行ルール

- **「話せる範囲で」を最初に明言する**。答えにくい質問は「パス」してよいことを冒頭でパネラー・会場の両方に伝える
- ファシリは**時間管理と話の振り分け**に徹する。自分の意見は最小限
- 2人に同じ問いを投げるときは、**交互に先攻を入れ替える**（片方に偏らないように）
- 1人の話が長くなったら「〇〇さんのところではどうでした？」でもう1人に振る
- 2人の対応が違う点（環境・組織規模・判断の速さ）はあえて拾い、**比較で深掘り**する
- 攻撃手法の具体的な再現方法（PoC の詳細）には踏み込まない。話が流れたら引き取る
- タイムキーパーを1人お願いできるとよい（残り時間カードを出してもらう）

### 6.3 配慮事項・発言ポリシー（パネラーと事前合意する）

- 顧客名・取引先名・具体的なシステム構成（IP、ホスト名、詳細なバージョン構成）は出さない
- **「まだ修正できていない環境がある」と特定できる発言は避ける**（攻撃者に情報を与えないため）
- 攻撃の痕跡が見つかったかどうかは、組織判断に従う（言えない場合は「ノーコメント」でOK）
- 撮影・SNS 投稿・録画／配信の可否を事前に決め、冒頭でアナウンスする
- 必要であれば、パネラーの所属組織の広報・セキュリティ担当の確認を取ってもらう

## 7. 事前ヒアリング項目（パネラー向け）

事前打ち合わせで確認する。答えられる範囲で OK。

1. 所属と役割（紹介時の表記）、アイコンやSNSアカウントの掲載可否
2. 担当している PHP 環境のざっくりした規模感（言える範囲で）
3. PHP2Shell をいつ・どこで知ったか
4. 実際にやった対応の流れ（ざっくりでよい）
5. 一番迷った・困った判断ポイント
6. 当日話してよいこと／話せないこと（NG リスト）
7. 録画・配信・SNS 投稿についての希望
8. 会場からの質問を受けてよいか
