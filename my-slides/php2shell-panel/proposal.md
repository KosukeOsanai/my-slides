## 2. 目的

本パネルは、PHP2Shell の技術的な仕組みの解説ではなく、**実際に対応にあたった人の「現場目線」で脆弱性対応を振り返る**ことを主眼に置く。

1. **現場のリアルな一次情報を共有する**
   - ニュースやアドバイザリでは分からない「第一報を見た瞬間の判断」「実際の対応の流れ」「迷ったポイント」を、当事者の言葉で聞く
2. **次の重大脆弱性に備えるヒントを持ち帰ってもらう**
   - 「影響範囲の棚卸し」「関係者との調整」「パッチ適用の判断基準」など、次に同じことが起きたときに使える知見を会場に残す
3. **「PHP本体の脆弱性」をアプリ開発者が自分ごと化するきっかけにする**
   - フレームワークやCMSの更新だけでは済まず、ランタイム（PHP本体）の更新が必要だったという点に目を向けてもらう

### イベントテーマとの関係

PHPカンファレンス新潟2026 のテーマ「新潟でかみしめて、つなぐ、つくる、つぎの未来へ。」（各語の意味は実行委員長 大沼佑樹「PHPカンファレンス新潟2026に向けて」より）との対応。

| テーマの語 | 意味 | このパネルでの位置づけ |
|------------|------|------------------------|
| かみしめ | 日々の経験や気づきを味わい直す | 3週間前の脆弱性対応を、当事者が振り返って言葉にする（企画の核） |
| つなぐ | 人と人、地域とコミュニティ、今と未来 | ある現場の知見を、会場の別の現場へ。今回の経験を次の脆弱性への備えへ |
| つくる | 新しい価値を生み出す | クロージングで「次に同じことが起きたときの自分たちの手順」を一言ずつ出してもらう |
| つぎの未来へ | — | 「次に同じことが起きたら」で締める |

本編との関係: 午後の本編には、松尾さん「PHPのバージョンアップ時にASTが変わらない変更の見抜き方」（14:10 B）、ざきさん「AI駆動で挑む！？レガシーPHPプロダクトのバージョンアップへの軌跡」（14:40 B）など、「PHP を上げる」話がある。クロージングで紹介して本編へつなぐ（後ろの枠を使う場合は「この直後に」と言える）。

## 3. 扱う内容

### 扱うこと／扱わないこと

| 扱うこと（現場目線） | 扱わないこと |
|----------------------|--------------|
| 第一報を受けたときの受け止め方・初動 | 脆弱性の内部構造の詳しい技術解説 |
| 影響範囲の調査、関係者との調整、暫定策の判断 | 攻撃手法・PoC の具体的な再現方法 |
| パッチ適用までの検証・リリース判断と、その懸念点 | 特定の組織・製品の対応への批評 |
| 「次はこうしたい」という振り返り | |

### 背景: PHP2Shell とは（オープニングのおさらい用）

> オープニングで共通認識をそろえるための最小限の情報で、深掘りはしない。
> **この節と「5. 問いかけ」に出てくる数値・日付・技術的な前提は、2026/10/28 時点の報道ベース。** 使う前に PHP 公式（php.net のリリースノート・セキュリティアドバイザリ）と NVD で裏取りし、違っていたら言い回しを直す。

- PHP 本体に見つかった 2 件の重大な脆弱性の通称（CVE-2026-109618 / CVE-2026-109619）
  - CVE-2026-109618: out-of-memory 時のメモリ破損によるリモートコード実行。FPM 環境で成立するかは、解析によって見解が割れていた
  - CVE-2026-109619: 古いグローバル状態（stale global state）が残ることによるリモートコード実行。セッションのアップロード進捗機能経由で FPM 上でも成立すると報告されている
- 深刻度: ベンダー評価で CVSS v4.0 9.2（評価機関によって差あり）
- 2026/10/21 に修正版 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 がリリース
  - EOL 版（7.4 / 8.0 / 8.1）向けのバックポートやディストリビューション独自パッチの情報もあり
- PHP 5.4 時代から存在していたバグとの報道あり
- 修正版の公開から数日後に、関連する別の脆弱性（CVE-2026-115560）への注意喚起と暫定策（アップロード進捗機能の無効化）が出たとの報道あり
- **ポイント**: WordPress やフレームワーク、プラグインの更新では直らない。PHP 本体の更新が必要

## 5. 問いかけ（ファシリ手持ち）

テーマに使える時間は合計20分なので、実際に聞けるのは各テーマ★の2〜3問程度。★は基本の問いで、依頼書にも例として載せている。「深掘り」は PHP2Shell ならではの特徴に絡めた質問で、★が話せなかったときや話が広がったときに使う。事前打ち合わせで、パネラーに「これなら話せる」ものを選んでもらう。

「何をしたか」は話せなくても「どう判断したか」なら話せることが多いので、判断の理由を聞く形にしている。

### テーマ1: 脆弱性を見たとき、どう思ったか（5分）

- ★最初にどこで知り、どんな第一印象を持ちましたか？（SNS／社内Slack／ベンダー通知／ニュース。「やばい」か「うちは関係ないかも」か）
- ★「PHP本体の脆弱性」と聞いて、アプリ側の脆弱性とどう違う緊張感がありましたか？

深掘り:

- CVSS はベンダー評価で 9.2（v4.0）、NVD では 9.8／8.1（v3.1）、10 と評価する調査会社も、と数字がばらつきました。数字の違いは対応の優先度に影響しましたか？
- 10 年以上前から残っていたバグだと言われています。「枯れた本体だから大丈夫」という感覚は変わりましたか？

### テーマ2: 現場でどういう対応をしたか（8分）

- ★最初の1時間／当日／1週間で何をしましたか？
- ★「PHP 5.4〜8.5 が影響」という範囲の広さを見て、該当する／しないを何で切り分けましたか？（バージョン／SAPI／設定／外部公開しているか）
- ★「修正版の公開前から悪用の試みが観測されていた」との報道がありました。「パッチを当てて終わり」ではなく「すでに侵入されているかも」という前提で動きましたか？

深掘り（切り分け）:

- CVE-2026-109619 は、デフォルトで有効なセッションのアップロード進捗機能（`session.upload_progress.enabled`）経由で成立すると言われています。この設定を意識したことはありましたか？ 自分たちの環境で有効かどうか、どう確認しましたか？
- CVE-2026-109618 が FPM 環境で成立するかは、解析によって見解が割れていました。「影響あり」とみなして動くか、情報がそろうのを待つか、どう決めましたか？
- 「認証なし・リモートから」という条件は、社内向けシステムや管理画面しかないサービスの優先度付けをどう変えましたか？
- CLI のバッチ、社内ツール、昔立てた WordPress のサイトなど、「メインの Web アプリ以外の PHP」はどこまで対象に入れましたか？ 見つけるのに苦労した場所は？

深掘り（時間と体制）:

- 修正版の公開は日本時間の夜（21日 23:00 ごろ、要確認）だったとの情報があります。その夜のうちに動きましたか、翌朝からにしましたか？ その判断の理由は？
- 前日に事前告知が出ていたとの情報があります。修正版が出るまでの間に準備できたことはありましたか？
- ライブラリなら `composer update` で済むところ、今回はランタイムの更新でした。誰の担当になりましたか？（アプリチーム／インフラチーム／ホスティング事業者）押し付け合いや抜け漏れは起きませんでしたか？
- 海外では政府系サイトをオフラインにした例も報じられました。「いったん止める」という選択肢は検討しましたか？ 検討したならどんな条件で？

深掘り（暫定策と侵害の確認）:

- WAF で防げると判断できましたか？ WAF のシグネチャが出るのを待ちましたか、それとも WAF だけでは不十分と考えましたか？
- 「修正前の数日間までさかのぼってログを確認すべき」という記事もありました。ログは、どの観点で見るのがおすすめですか？
- メモリ上のパスワードやセッショントークンが漏れる可能性も指摘されていました。シークレットのローテーションやセッションの強制ログアウトは、どんな条件なら必要だと考えますか？
- GitHub に PoC やチェックツールを名乗るリポジトリが大量に出ました。こうしたツールとはどう付き合うのがよいと思いますか？（偽物・マルウェア入りの可能性も含めて）

### テーマ3: パッチ適用にあたって何が懸念点だったか（7分）

- ★検証はどこまでやり、何を基準にリリースを判断しましたか？
- ★PHP 本体の入れ方（ディストリビューションのパッケージ／自前ビルド／公式 Docker イメージ）によって、更新のしやすさはどう違いましたか？
- ★EOL の PHP バージョンが残っていた場合、どうしましたか？（バックポートを使う／移行を前倒しする）

深掘り:

- パッケージを更新しても、動いているプロセスが古いままでは直りません。php-fpm や常駐型の実行環境（FrankenPHP のワーカーモード、RoadRunner、Swoole など）の再起動まで確認しましたか？
- 「本当に直った」はどう確認しましたか？ ディストリビューションのバックポート版はバージョン番号が変わらないので、`php -v` やスキャナーの結果と食い違うことはありませんでしたか？
- 公式 Docker イメージを使っている場合、イメージの更新を待ちましたか？ ベースイメージを差し替えて全サービスを再ビルド・再デプロイするのは大変でしたか？
- 止められないサービスで、メンテナンス時間の確保はどう調整しましたか？
- 続報の CVE-2026-115560 には専用パッチがなく、アップロード進捗機能の無効化が暫定策とされていました。この暫定策を入れるかどうかは、何を基準に判断しますか？ 入れるなら、アプリ側で何を確認しておくべきですか？
- WordPress などの CMS を使っているお客さんやチームに「プラグインやテーマを更新しても直らない」と伝える必要はありましたか？ どう説明しましたか？
- EOL のバージョン向けにもバックポートが出たことは、「EOL でも何とかなる」という安心材料ですか、それとも早くバージョンアップすべきという警告ですか？

### クロージング（4分）

- ★次に同じレベルの脆弱性が出たら、今回の経験から何を変えますか？（一言ずつ）
- 深掘り: AI を使った調査で見つかったと報じられています。同じレベルの脆弱性が今後増えるとしたら、何を備えておきますか？
- ファシリまとめ: 3つくらいのキーワードに集約して締める（例:「棚卸し」「判断の速さ」「ランタイムも依存関係」）。そのあと午後の本編を紹介する

### 会場を巻き込む質問（パネラーが話しにくいときの場つなぎ）

- 挙手アンケート:「PHP2Shell の対応をした人？」「`session.upload_progress` という設定を今回はじめて知った人？」「修正版を当てたあと、php-fpm の再起動まで確認した人？」
- 手が挙がった人数に対して、パネラーにコメントをもらう（「思ったより多い／少ない」から話を広げる）

### 6.2 当日の進行ルール

- **「話せる範囲で」を最初に明言する**。答えにくい質問は「パス」してよいことを冒頭でパネラー・会場の両方に伝える
- ファシリは**時間管理と話の振り分け**に徹する。自分の意見は最小限
- 2人に同じ問いを投げるときは、**交互に先攻を入れ替える**（片方に偏らないように）
- 1人の話が長くなったら「〇〇さんのところではどうでした？」でもう1人に振る
- 2人の対応が違う点（環境・組織規模・判断の速さ）はあえて拾い、**比較で深掘り**する
- 発言ポリシー（依頼書の「お話しいただくうえでのお願い」）から外れそうになったら、ファシリが引き取る
- タイムキーパーを1人お願いできるとよい（残り時間カードを出してもらう）

アンカンファレンス枠ならではの注意点:

- 昼休憩中（お弁当の時間）なので、途中から来る人・途中で抜ける人がいる。各テーマの冒頭で「今は〇〇の話をしています」と一言入れて、途中からでも話に入れるようにする
- 参加者の多くは PHP2Shell の詳細を知らない前提で話す。おさらいでは「PHP 本体の脆弱性」「パッチ（修正版）」「暫定策」など、基本の言葉から説明する
- SAPI・FPM・`session.upload_progress` などの専門用語は、出てきたらファシリが一言で補足する（例:「FPM は、Web サーバーから PHP を動かす仕組みの一つ」）
- 「言語を問わず通じる話」（ランタイムや基盤の脆弱性への向き合い方）を意識して拾い、PHP がメインでない方も持ち帰れるようにする

### 6.3 発言ポリシー

パネラーと合意する内容は、依頼書（request.md）の「お話しいただくうえでのお願い」を正とする。ファシリ側で追加で気をつけること:

- 撮影・SNS 投稿の可否はパネラーの希望を聞いたうえで決め、冒頭で会場にアナウンスする
- 開催時点で修正版が出ていない関連の脆弱性（CVE-2026-115560 など）があれば、具体的な攻撃条件に話が及ばないよう、暫定策の話で止める

|--------|--------|
| パネラーが1名しか決まらない | ファシリとの対談形式にする（時間配分は同じ） |
| 所属組織の許可が出ない、話せる範囲が狭い | 「5. 問いかけ」の判断の理由・一般論を聞く質問に寄せる。それも難しければ別の候補に打診する |
| 直前に新しい CVE やパッチが出る | おさらいスライドを更新し、扱うかどうかを当日の直前確認で決める |
| 当日パネラーが来られなくなる | 1名なら対談形式にする。2名とも来られない場合は、枠をアンカンファレンスに戻す |
| 話が止まる、盛り上がらない | 会場を巻き込む質問（挙手アンケート）でつなぐ |
| 時間が押す | 会場質問を削る。後ろの枠なら 14:00 で必ず終える |
